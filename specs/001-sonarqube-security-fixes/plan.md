# Implementation Plan: SonarQube Security Findings Remediation

**Branch**: `001-sonarqube-security-fixes` | **Date**: 2026-05-21 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/001-sonarqube-security-fixes/spec.md`

## Summary

Clear two SonarQube findings on the DNN Platform fork:

1. **secrets:S6703 (Blocker)** — replace `Password=sa` / `Password=` literals in the
   AdoNetAppender XML-doc examples with neutral placeholders.
2. **csharpsquid:S5445 (High)** — replace `Path.GetTempFileName()` with a secure pattern
   (`Path.GetTempPath()` + `Path.GetRandomFileName()` + explicit `FileStream` creation +
   guaranteed cleanup).

Approach: introduce a single, reusable **`SecureTempFile`** abstraction in a new shared
library `DotNetNuke.Security.IO`, multi-targeting **`net8.0;net48`**, and migrate every
production call site of `Path.GetTempFileName` in the repo to consume it. Tests are written
**first** (TDD) for the security-fix scenarios, then additional integration tests cover the
behavior on the .NET 8 target. The rest of the DNN Platform stays on .NET Framework 4.8 — per
the user's clarification, "migration to .NET 8+" means **new code is .NET 8+**, not a
platform-wide rewrite (Web Forms cannot run on .NET 8 and a full migration is out of scope).

## Technical Context

**Language/Version**: C# 12, multi-target **`net8.0;net48`** for the new
`DotNetNuke.Security.IO` library and its tests. Consumers stay on their current targets
(`net10.0` for `Build/`, `net48` for `DNN Platform/*` libraries). SDK pinned to `10.0.300` in
[global.json](../../global.json).

**Primary Dependencies**:
- New library: zero runtime dependencies (uses BCL `System.IO` only).
- Tests: **xUnit 2.x** + **FluentAssertions 6.x** (per user clarification). Note: existing DNN
  test projects use NUnit; the new test project is the first xUnit project in the repo. This is
  documented as an intentional divergence in Complexity Tracking.
- Build task migration (`Build/Tasks/UpdateDnnManifests.cs`) keeps Cake.Frosting on `net10.0`.

**Storage**: N/A (the abstraction creates files in `Path.GetTempPath()`; consumers manage their
own content).

**Testing**: xUnit + FluentAssertions; tests target both `net8.0` and `net48` to prove the
abstraction behaves identically on both. Run via `dotnet test` from the solution root.

**Target Platform**: Windows (DNN's existing target). The temp-file logic uses portable BCL
APIs so it would also work on Linux/macOS for the new library; not tested on those platforms
in this feature.

**Project Type**: Library extension for an existing large .NET Framework codebase + new
multi-target class library.

**Performance Goals**: No measurable regression vs. `Path.GetTempFileName` — temp-file creation
is a one-shot operation per build/request, not a hot path.

**Constraints**:
- MUST NOT break the existing DNN Platform .NET Framework 4.8 build.
- MUST NOT introduce a runtime dependency that is unavailable on net48 (rules out modern
  packages that dropped net48 support).
- MUST be consumable from both Cake build tasks (net10.0) and DNN libraries (net48).

**Scale/Scope**: ~6 production call sites to migrate (+ 1 new library + 1 new test project).
Total touched files estimated at ~10–15.

## Complexity Tracking

> Filled because **Principle II (Minimal-Diff)** is being relaxed, with user authorization.

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Cross-file refactor: 5 call sites migrated beyond the SonarQube-flagged file | The same insecure pattern exists in 5 other production files (RssDownloadManager, OpmlDownloadManager, FileResponseFilter, FileProvider, plus 1 test subject). Adding a single helper now is one PR; fixing them individually as SonarQube flags each one over time is six. User explicitly authorized this in `/speckit-specify` ("a refatoração pode reajustar o problema em vários arquivos para uma melhor manutenção"). | Fix only `Build/Tasks/UpdateDnnManifests.cs` — leaves the insecure pattern in 5 other files where SonarQube will eventually re-flag it, defeating the purpose of fixing it once. |
| New library project `DotNetNuke.Security.IO` | Hosting the helper inside an existing project would either (a) couple `Build/` to DNN runtime libraries (bad layering) or (b) duplicate the helper in two places (defeats DRY/SRP). A small focused library is the cheapest shared home. | Place the helper inline in each consumer — duplicates code, violates DRY, makes future SonarQube hits whack-a-mole again. |
| Multi-target `net8.0;net48` for the new library (introducing a .NET 8 build artifact) | User explicitly requested .NET 8+ for new code. The helper must also be consumable from existing net48 DNN libraries, so the library multi-targets. This is the minimum way to honor "migrar para .NET 8+" without rewriting DNN's Web Forms core (which doesn't run on .NET 8). | Stay on net48 only — does not satisfy the user request. Move to net8.0 only — breaks the net48 consumers. |
| New xUnit + FluentAssertions test project (DNN tests historically use NUnit) | User explicitly chose xUnit + FluentAssertions in the clarification step. xUnit also has cleaner support for theory/data-driven tests we'll use for the cross-target matrix (net8.0 × net48). | NUnit — matches the existing convention but contradicts the user's explicit choice. The divergence is local to one new test project, so the inconsistency cost is low. |

## Phase 0: Outline & Research

Output: [research.md](research.md). Resolves:

- Secure temp-file pattern on .NET (chosen: `Path.GetTempPath` + `GetRandomFileName` +
  `FileStream(..., FileMode.CreateNew, FileAccess.ReadWrite, FileShare.None,
  bufferSize, FileOptions.DeleteOnClose)`).
- Multi-targeting `net8.0;net48`: how to keep one source file working under both, conditional
  compilation only where strictly needed (`#if NET8_0_OR_GREATER` for any newer BCL API).
- SonarQube verification mechanics in the absence of a CI scan (manual rule check fallback).
- xUnit + FluentAssertions setup for a multi-target test project, test-discovery on net48.
